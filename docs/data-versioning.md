# 数据版本与升级迁移

状态：已实施（2026-11-28）。v0.1.0 是第一个公开版本，从 v0.2.0 起，所有本机数据的格式变化都按本文处理。

## 1. 现状

| 数据 | 位置 | 版本标记 | 问题 |
|---|---|---|---|
| 书库：书目、阅读进度、生词与复习状态、指纹 | `library.json` | `version: 2` | v1 迁移是写在 `LibraryStore` 里的特例代码，没有统一框架 |
| 阅读用正文 | `books/<id>/content.json` | 无 | 导入时生成一次，之后再不更新。导入/渲染改进后，旧书只能重新导入（新 UUID，进度和生词就和书断开了） |
| 原书内容 | `books/<id>/book.json`、`docs/`、`res/` | 无 | 无损保存，但没有版本标记 |
| 章节信息（标题、长度） | `library.json` 里每本书的 `chapters` | 随书库 | 是从正文算出来的，却存在用户数据里，正文变了它就过时 |
| 阅读设置、翻译设置、AI 端点 | UserDefaults，键名散落在各个视图里 | 无 | 改键名或改值的含义时没有迁移手段 |
| API Key | Keychain | 无 | 账户名约定写在代码里 |
| 词典包 | Application Support/Readling/Dictionaries | `schema` + `version` | 下载内容，有自己的版本机制，不纳入本文 |

还有一个隐患：`TextStyleRun.Style` 这类枚举，遇到不认识的取值时，整章都会解码失败。

## 2. 基本原则

1. **数据分两类。**
   - **源数据**：丢了就无法找回。包括书库（进度、生词、复习记录）、原书内容（`book.json`/`docs/`/`res/`）、设置、Key。这类数据由迁移步骤转换格式。
   - **派生数据**：可以从源数据重新算出来。包括 `content.json`、章节信息、封面缩略图。这类数据不做格式转换，由迁移步骤要求**从源数据重建**。

   今天的问题，就是把派生数据 `content.json` 当成了源数据，只生成一次。
2. **整个数据目录只有一个版本：最后一次迁移到的 app 版本。** 不给每个文件各定一套版本号。
3. **只在相邻的已发布版本之间迁移。** 跨多个版本升级时，依次执行各个迁移步骤。
4. **不允许带着数据降级**，和 iOS 一样（见 3.6）。
5. **存下来的枚举要容忍未知值。** 遇到不认识的取值，丢掉这一条或退回默认值，不能让整个文件解码失败。
6. **迁移和重建的状态在界面上可见**（见第 5 节）。

## 3. 迁移

### 3.1 数据版本
- `Application Support/Readling/data-version.json` 记录 `{"appVersion": "0.2.0"}`，即这份数据当前对应的 app 版本（SemVer）。
- 文件不存在时：有 `library.json`，就是 v0.1.0 的数据；什么都没有，就是全新安装，直接写入当前版本。
- `library.json` 里原有的 `version` 字段保留，书库结构变了就加一。v0.1.0 只认这个字段，遇到更大的值会进入只读，这样它也不会覆盖新数据。

### 3.2 迁移链
- 代码里有一份**版本列表** `DataVersion.chain`（见 `Readling/Persistence/DataVersion.swift`），如 `["0.1.0", "0.2.0", …]`，开发中的版本放在最后。发布脚本核对它和 git 的 `v*` tag 一致。
- **相邻两个版本之间有且只有一个迁移步骤**，比如 `Migration_0_1_0_to_0_2_0`。数据没有变化的版本之间也要有一个步骤，写成空步骤即可（`Tools/app_release.py prepare` 在无新步骤时会自动生成），这样迁移链是连续的，一眼能看出每次升级做了什么。
- 跨多个版本升级时（如 0.1.0 → 0.4.0），就依次执行 0.1→0.2、0.2→0.3、0.3→0.4。**没有跨版本的捷径步骤。**
- 一个步骤负责这次升级涉及的全部数据，不按文件拆成多套迁移。它可以做两件事：
  - **转换源数据**：书库、原书内容的描述文件、设置、Keychain；
  - **要求重建派生数据**：调用 `context.requestRebuild(.content)`（正文）。

### 3.3 步骤的写法
```text
Readling/Persistence/
  DataVersion.swift              版本列表、迁移链、读写 data-version.json
  Migrator.swift                 找到起点，按顺序执行，日志化统一提交，记录历史
  TextRemap.swift                新旧章节按词对齐换算偏移、重建队列 rebuild-queue.json
  Migrations/
    Migration_0_1_0_to_0_2_0.swift
    …
  Snapshots/
    V0_1_0.swift                 v0.1.0 存储结构的冻结副本（library、设置键）
    V0_2_0.swift
```
- 每个步骤是一个纯函数：输入“上一版的数据快照”，输出“这一版的数据快照”和要求的重建。它只用 `Snapshots/` 里的冻结结构，**不引用会继续变化的现行模型**。现行模型变了，旧步骤也不会跟着变。
- 迁移链的最后一步输出当前版本的快照，再由现行模型加载。这一层衔接由夹具测试保证（见 3.7）。
- **版本发布后，它的快照和迁移步骤就冻结，不再修改、不再删除。** 发布之前，从上一个已发布版本到开发中版本的那一步可以随意修改。开发设备上的数据如果已经被旧写法迁移过，可以在“数据”页里用“从备份重新迁移”（仅开发版提供，见第 5 节）重跑一遍。

### 3.4 执行与落盘
启动时，在加载任何数据之前：
1. 读取数据版本，从迁移链里找出起点。数据版本比应用新，就按 3.6 处理；等于当前版本就跳过迁移。
2. 在内存里依次执行各个步骤，中间结果不落盘。合并各步要求的重建。
3. 统一提交：
   - 把要改的文件先写成 `*.migrating`；
   - 写一个 `migration-journal.json`，列出待替换的文件、目标版本和待重建的书；
   - 逐个改名替换（原文件先另存为 `*.<原版本>.bak`）；
   - 把待重建的书写进 `rebuild-queue.json`，更新 `data-version.json`，在 `migration-history.json` 里追加一条记录，最后删除日志。

   中途中断时，下次启动看到日志，就把未完成的替换做完。任何一步失败都保留原文件，书架显示“重试 / 另存”（沿用现有的 `readFailure` 机制）。
4. 备份保留到下一次迁移成功为止。

源数据都是小文件，迁移通常不到一秒。超过半秒时，启动画面上显示“正在升级数据…”。

### 3.5 重建（由迁移触发）
重建在迁移提交之后、在后台逐本进行。耗时的部分不阻塞启动；失败了可以继续用旧正文。

**导入和重建走同一条路。** 现在导入是一边解 ZIP、一边渲染章节，所以无法单独重建。改成两步：
1. `BookImporter`：只负责把 EPUB/TXT 安全地解包成书的目录（`book.json`、`docs/`、`res/`），保留现有的全部安全检查和数量限制。
2. `BookBuilder.build(from: BookDirectory)`：只从书的目录读取（OPF、目录、spine、文档树或原字节），生成正文。导入时调用它，重建时也调用它，只有这一份实现。

**偏移换算。** 正文变了，阅读进度和生词（章节序号 + 偏移）都要换算。链接锚点随正文重新生成，不需要换算。
- **按来源文档对齐**：一个 spine 文档可能被拆成几章。把同一来源的旧章节拼接起来，和新章节逐文档对齐；TXT 整本书算一个文档。这样章节数量变化也能处理。
- **按词对齐**：两边都切成可见的词元，包括单词、标点和附件字符 U+FFFC。用 patience diff 求公共子序列（`Alignment.match`）：先匹配相同的开头和结尾，中间以两边都只出现一次的词元为锚点、取顺序一致的最长一串，再在锚点之间重复；只有没有锚点的短片段（两边合计不超过 2000 个词元）才用 Myers diff（Swift 的 `CollectionDifference`）精确比较。不对整个文档直接跑 Myers：它的时间和内存随差异量平方增长，整本 TXT 改动一多就要几分钟。偏移落在一个保留下来的词元上，就映射到新文本中对应的位置；落在被删除的词元上，就映射到前一个保留词元的末尾。现有的 `OffsetMap` 只能处理只差空白的情况，换成这个通用实现。
- **生词再校验**：换算后，在新位置附近找生词的 `selection`。找不到就在本章搜索 `sentence`，再找不到就保留换算出的位置。

**保证正文和书库一致。** 正文和书库必须同时更新，不能出现正文换了、偏移还是旧的。
1. 新正文写到 `content-<n>.json`；
2. 提交书库：这本书的 `contentFile`、`chapters`、进度和这本书的生词，一次原子写入；
3. 删除旧的正文文件，把这本书从 `rebuild-queue.json` 里移除。

任何一步中断，书库指向的都是一份完整、一致的正文。

**时机。** 迁移完成后，在后台逐本重建。如果用户打开了还没重建的书，就先重建这一本（显示进度），再打开。重建失败的书继续用旧正文，记下原因，下次启动再试。v0.1.0 之前导入、没有原书内容的书（`hasPackage != true`）无法重建，保持原样，并在“数据”页注明。

**防止忘记触发重建。** `DataMigrationTests` 用最新的已发布版本数据夹具里的书籍运行 `BookBuilder.build`，和夹具中保存的章节直接比较：输出变了，而还没有开启下一版迁移步骤或该步骤没有要求重建正文，测试就失败。

### 3.6 降级：和 iOS 一样不允许带数据降级
App Store 本身不能装旧版本，只有通过 iosign 等方式侧载时才会遇到。数据版本比应用新时：
- 不读取、不写入任何数据；
- 整屏提示（`NewerDataView`）：“这台设备上的数据来自 Readling x.y.z，当前安装的是 a.b.c。旧版本不能读取新版本的数据，请安装 x.y.z 或更高版本。”
- 唯一的操作是“另存数据并重新开始”：把整个数据目录改名留着，不删除，然后以空书库启动。

### 3.7 测试
- `ReadlingTests/Fixtures/AppData/<版本>.bundle`：每个已发布版本保存一份真实数据目录，用当时 tag 上的代码生成。内容包括：书库（有阅读进度、生词，含复习状态和机器翻译释义）、一本含公式和表格的 EPUB（`formulas.epub`）、`alice.epub`、一本 TXT（`verse.txt`）、一组设置。
- 每个夹具都要迁移到当前版本并完成重建，检查：现行模型能加载；进度和生词仍指向原来那个词；设置的取值不变。
- 迁移链检查：`DataVersion.chain` 里每对相邻版本都恰好有一个步骤且首尾相接；`SettingsKeys.all` 与当前快照一致。
- 中断与失败：日志恢复能完成替换；某一步抛错时原文件不变；数据版本比应用新时不读不写；从备份重新迁移能完整复现。

## 4. v0.2.0 的第一个迁移步骤 `Migration_0_1_0_to_0_2_0`

- 书库：`version` 2 → 3。每本书增加 `contentFile`，取值为 `"content.json"`；其余字段不变。
- 设置：键名集中到 `SettingsKeys.swift` 一处定义，视图里不再直接写字符串。这次没有改名，所以不需要迁移设置。
- 重建：所有有原书内容的书都重建正文，这样公式、表格、分隔线、列表编号就会出现。
- 写入 `data-version.json`，记录迁移历史。

## 5. 界面：设置 › 关于 › 数据与升级（`DataStatusView.swift`）

| 区块 | 内容 |
|---|---|
| 版本 | 应用版本；数据版本 |
| 上次升级 | 时间、0.1.0 → 0.2.0、结果（成功 / 失败及原因）；“升级历史”推入完整记录 |
| 正文更新 | 进行中：“正在更新 3/12：《Alice's Adventures in Wonderland》”，配进度条；完成：“全部书籍已是最新”；失败：列出书名和原因，配“重试”按钮；不能更新的书（没有原书内容）单独列出并说明原因 |
| 备份 | 迁移前的备份占用多少空间；可以手动清理 |
| 仅开发版 | “从备份重新迁移”：用备份恢复到迁移前，再重跑一遍迁移链 |

书架上不额外显示；打开还没更新的书时，阅读页先显示这本书的更新进度。

## 6. 发布流程

`Tools/app_release.py` 增加检查：
- **prepare**：若本次版本还没有开启新的迁移步骤，校验上一版夹具已存在，并自动生成新版本的空快照、空迁移步骤并追加到 `DataVersion.chain`；若开发中已开启该版本的迁移步骤则直接沿用。
- **check**：核对 `DataVersion.chain`、快照文件、迁移步骤文件、已合并的 git `v*` tag 以及所有先前版本的 `AppData/<版本>.bundle` 夹具一致；如果当前步骤要求重建正文，`--require-notes` 要求发布说明“升级与兼容”一节写明已导入的书会自动更新。
- **fixture**（发布后）：在新 tag 上运行 `python3 Tools/app_release.py fixture` 生成并提交 `ReadlingTests/Fixtures/AppData/<版本>.bundle`。

在 AGENTS.md 的“约定”里加一条简短规则，指向本文。

## 7. 已决定

- v0.1.0 之前的开发期格式不再支持，迁移链从 0.1.0 开始。相关兼容代码已删除：书库 `version: 1` 的迁移、`books/<id>.json` 与 `books/<id>-cover.jpg` 平铺文件、只按空白对齐的 `OffsetMap`。
- 不允许带数据降级（3.6）。
- 迁移完成后在后台全部重建，打开还没重建的书时优先处理这一本（3.5）。
